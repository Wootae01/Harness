# /harness:review — 통과할 때까지 반복하는 자가 검토

> 🇰🇷 한국어 번역본입니다. 정본(에이전트가 읽는 문서)은 [SKILL.md](SKILL.md)이며, 내용이 다르면 영어본이 우선합니다.

목표: **사람이 볼 필요가 없는 수준까지** 스스로 끌어올린다. 검토자가 만족할 때까지 고치고 다시 본다.

## 1. 범위 파악
- `git status --short`, `git diff` (+ `git diff --staged`). 인자가 있으면 그 경로만 본다.
- 관련 실행 계획(`docs/exec-plans/active/`)과 스펙(`docs/product-specs/`)이 있으면 완료 조건을 읽는다.

## 2. 기계적 검사 — 먼저 실행하고, 실패하면 고친 뒤 다시 실행
```bash
node "${CLAUDE_PLUGIN_ROOT}/scripts/check-docs.mjs"
# + 프로젝트 CLAUDE.md §5 명령어 표의 lint / typecheck / test (비어 있으면 그 사실을 보고에 적는다)
```
검사를 끄거나 건너뛰어서 통과시키지 않는다.

## 3. 판단 검사 — 기계가 아직 못 잡는 것
`ARCHITECTURE.md` §3에서 상태가 **📄 문서만**인 불변식을 diff에 하나씩 대조한다. 추가로 다음을 확인한다.

| 관점 | 질문 |
|---|---|
| 정확성 | 스펙의 수용 기준을 실제로 만족하는가? 경계 조건, 빈 값, 에러 경로는? |
| 경계 검증 | 외부 데이터를 추측한 모양으로 쓰고 있지 않은가? (G-2) |
| 레이어 | 의존성이 Domain을 향하는가? Domain에 프레임워크/DB/HTTP import가 없는가? Presentation이 Infrastructure를 직접 쓰지 않는가? |
| 재사용 | 이미 있는 공유 유틸이나 컴포넌트를 다시 만들지 않았는가? (G-1) |
| 패턴 | 나쁜 기존 패턴을 복제하지 않았는가? (G-4) |
| 문서 | 새 결정, 새 env 키, 새 의존성이 문서(와 `.kr.md` 번역본)에 반영되었는가? (G-5) |
| 검증 | 실제로 실행해서 확인했는가? (테스트만이 아니라 앱 동작까지) |

## 4. 반복
- 문제를 찾으면 **고치고 2단계부터 다시 한다.** 최대 3회까지 반복한다.
- 3회 후에도 남은 문제가 판단의 문제(제품 결정, 불변식 변경)라면 멈추고 사람에게 질문한다.
- 같은 지적이 반복되면 → 린트나 테스트로 승격하자고 제안한다 (`ARCHITECTURE.md` 불변식 표에 추가).

## 5. 보고 (짧게)
```
검토 결과: ✅ 통과 / ⚠️ 사람 판단 필요
- 기계 검사: check-docs ✓, lint ✓, test ✓
- 고친 것: ...
- 남은 것 / 질문: ...
- 승격 제안: ...
```
통과하면 `/harness:commit-message`를 안내한다.
